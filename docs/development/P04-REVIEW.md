# P04 implementation review — 19 September 2026

P04 is in progress, not released. Build-order steps 1 (contracts, migration, permission and capability definitions), 2 (domain and accounting rules), 3 (API and jobs), 4 (user journeys) and 5 (acceptance and operations) are implemented; no `sales` capability is activated for a live tenant and no tax rule version is active anywhere.

## P04-01 contracts and migration

Contracts: the 34 P04 operations (`/tax-rules` create/list/get/edit/approve/activate, `/invoices` create/list/get/edit/submit/approve/post/correct/deliver, `/sales-orders` create/list/get/edit/submit/approve/convert, `/collections` create/list/get/edit/submit/approve/post/reverse/allocations, `GET /open-items`, `POST /allocations/{id}/reverse`) and their schemas (`TaxRuleCreate/Resource`, `DocumentCreate/Line/Resource/Correction`, `OpenItemView/List`, `ApplyAllocations`, `Allocation`) were already in the reviewed OpenAPI and are compiled by `@lara/contracts`; the P02 API returns `FEATURE_NOT_ENABLED` for them until P04-03. The P04 permissions (`tax_rule.*`, `invoice.*`, `open_item.read`, `collection.*`, `allocation.reverse`) and the `sales` capability (depends on `general_ledger`) were seeded by migration `0009`, so no contract or seed change was needed for this ticket. Settlements (`/settlements`) are P05 operations in the contract; P04 stores receipts in the shared `settlements` table (direction `receipt`) and exposes them as collections.

Migration `0016_p04_sales_and_tax_schema.sql` adds the sales and tax-kernel tables from the shared data contract (`05-data-and-accounting.md`) and the P04 specification:

- `tax_rule_versions`: versioned rules per entity and code (`tax_type` vat/withholding/grt/dst/percentage, rate in [0,1], basis, recognition, line or document rounding, validity window), each requiring at least one source evidence id and one golden case id. Status machine `draft → pending_approval → approved → active → superseded` (or `rejected`) enforced by trigger; approver and activator must differ from the author (`SELF_APPROVAL`); rate, basis, recognition, rounding, validity and content hash are immutable once approved; one active version per code (`tax_rule_versions_one_active`). Fixtures stay draft: nothing in the migration activates a rate.
- `document_series` and `number_events`: one active series per branch and kind; the counter never moves backwards; an exhausted series is replaced, never reopened; every issued, skipped or voided number is an append-only event with one `issued` event per number, so unused numbers are explained (P04-T02 at the database layer).
- `payment_terms` (installments JSON), `credit_limits` (one approved limit per party and currency, separate approver) and `deliveries` (recipient hash, template version, state, provider reference, attempts; the worker may update deliveries and the document's `delivery_state`/`reporting_state` projections but nothing else on documents).
- `documents`, `document_lines`, `document_relations`, `party_snapshots`: header totals `gross = net + tax` and line totals are checked, and a deferred constraint trigger refuses a commit whose header differs from its line sums, so input totals cannot override the server computation (P04-T01). State machine `draft → submitted → approved → posted`, with `changes_requested`, return to draft and `cancelled` as terminal; the approver differs from creator and submitter; a material edit (payload hash) outside draft is refused; `posted` requires a journal entry and posting actor and freezes header, lines, official number and series; official numbers require a series, are unique per series and are never reassigned. Relations (`correction`, `credit`, `replacement`, `order`, `receipt`, `reversal`, `advance_application`) and party snapshots are append-only.
- `tax_events`: recognized once per document, line, rule version and recognition; the only permitted change is recording `reversed_by`.
- `open_items`, `settlements`, `allocation_events`: an open item's identity and original amount are immutable; the outstanding amount is derived by `lara.open_item_allocated()` from append-only allocation events. The insert guard locks the settlement then the item, requires a `posted` settlement, matching party, currency and side (receipts settle AR, payments settle AP), and refuses any apply beyond the item's outstanding or the settlement's unallocated amount (`ALLOCATION_EXCEEDS_BALANCE`, P04-T03); a `reverse` must mirror one `apply` of the same settlement and item with a reason, and each apply can be reversed once. Settlement components (`cash + withholding + adjustment = gross`) are checked; posted settlements are immutable and move only to `reversed` with a reversal entry.
- Row-level security is enabled and forced on every table with the tenant policy; runtime grants follow the P02 pattern (`lara_api` inserts/updates, no DELETE on financial facts, DELETE only on draft document lines; `lara_worker` reads plus delivery projections; `lara_audit_reader` read-only). `scripts/tenant-teardown.mjs` and `scripts/snapshot-lib.mjs` include the new tables for test teardown and restore rehearsals.

Postings for documents and settlements go through `lara.post_journal_entry` with `sourceType` `document`/`settlement`, so CORE-01–09 apply unchanged; the domain layer (P04-02) computes tax snapshots and creates open items in the same transaction.

Verification: `scripts/test-p04-schema.mjs` (also in `scripts/ci-database.mjs` for fresh and upgrade databases): eight groups against real PostgreSQL through the runtime role covering tax rule lifecycle and immutability, numbering, document totals, state machine and posted immutability with the AC-01 posting (Dr AR 11,200 / Cr Revenue 10,000 / Cr Output tax 1,200), tax events, allocations with the AC-02 receipt (partial, over-allocation, settled, reverse, cross-currency, wrong side and wrong party refusals), credit limits and worker grants, and tenant isolation. `scripts/test-foundation-db.mjs` rehearses the migration in a rollback namespace and `scripts/test-restore.mjs` snapshots the new tables.

Follow-up migrations: `0017_p04_credit_allocations.sql` aligns `documents.settlement_state` with the contract enumeration (`unpaid`, `partial`, `paid`, `credit_balance`) and lets an allocation event originate from a posted credit note (`credit_document_id`, exactly one source) so a credit reduces the original open item through the same guarded, append-only path (`lara.credit_allocated()`); `0018_p04_settlement_allocation_intents.sql` stores a receipt draft's intended allocations, applied only when it posts.

## P04-02 domain and accounting rules

`packages/domain/src/sales.mjs` implements the P04 rules over the schema, gated on the `sales` capability and an approved `sales_profile` settings version (AR, output tax, cash and withholding receivable accounts, currency scale, due days, `reportingRequired`, `enforceCreditLimits`):

- Tax kernel: `computeLines(lines, rules)` is a pure function in BigInt at 1e-12 precision. Exclusive lines: `net = round(q × price − discount)`, `tax = round(net × rate)`; inclusive lines: `gross = round(q × price − discount)`, `net = round(gross / (1 + rate))`, `tax = gross − net`; half up at the currency scale, once. A rule version with `document_half_up` rounds the exact sum of its lines' tax and allocates the residual cents to the largest fractional remainders, ties by line number (P04-T04, including the 0.01 residual). Mixed bases are summed per line, never classified by header. Header totals are the sums of the computed lines; the request carries no totals, so input cannot override server tax.
- Tax rule versions: created with available evidence and known golden case ids (the API passes the accounting-cases catalog), approved and activated by principals other than the author, immutable once approved; activation supersedes the active version of the same code and publishes `rule.activated.v1`. Lines reference a rule by any version id; the version active on the document date is snapshotted per line.
- Documents (invoice, credit note, quotation, sales order; bills and purchase orders return `FEATURE_NOT_ENABLED` until P05): customer role required, revenue lines never post to control accounts, `draft → submitted → approved → posted` with content-version-bound approval by a principal other than preparer or submitter, material edits return to draft, cancellation only before approval. Issuance (`POST /invoices/{id}/post`) is the single financial effect in one transaction: the next number of the branch's active series under a row lock with an `issued` number event, the party snapshot, `lara.post_journal_entry` with `sourceType=document` (AC-01: Dr AR gross / Cr revenue per account and dimensions / Cr output tax), tax events per line for `issue`/`accrual` recognition, and the open item. A failed issuance rolls its number back; a repeated post returns the same entry (P04-T02). `reportingRequired` profiles refuse issuance with `FEATURE_NOT_ENABLED` until the `compliance` capability (P07) is active while drafting continues (P04-T05).
- Corrections (`POST /invoices/{id}/correct`): `credit_note` (partial, within the remaining creditable net per revenue account after prior credits), `additional_invoice` and `reversal` (full credit) create linked drafts (`document_relations` credit/correction/reversal) that travel through review; the posted credit (AC-06: Dr revenue / Dr output tax / Cr AR) applies to the original open item up to its outstanding, the rest stays as `credit_balance` (P04-T03).
- Collections (receipts): `gross = cash + withholding`, allocation intents validated against the customer's open items and the receipt amount, submit/approve/post with the same separation of duties; posting writes AC-02/AC-05 (Dr cash / Dr withholding receivable / Cr AR) and applies the intents as guarded allocation events. `POST /collections/{id}/allocations` applies more from a posted receipt (the database refuses any amount beyond the item's outstanding or the receipt's unallocated balance, so the same receipt never allocates twice), `POST /allocations/{id}/reverse` mirrors one apply once, `POST /collections/{id}/reverse` posts the mirrored entry, unwinds open allocations and leaves the receipt as an immutable `reversed` fact. Document `settlementState` is derived after every allocation change.
- Orders: approved quotations and sales orders convert once into an invoice draft for the remaining billable quantity per line with an immutable `order` relation. Credit limits: an approved limit gates invoice submission against outstanding receivables. Deliveries: `POST /invoices/{id}/deliver` records a delivery with a hashed recipient and queues a `document.deliver` job; the document keeps the projection state. Open items list allocated and outstanding amounts from allocation events; `agingReport` buckets outstanding receivables per customer as of a date.

Verification: `scripts/test-p04-domain.mjs` (nine groups, also in CI for fresh and upgrade databases) covers capability and profile gates, the tax rule lifecycle, the rounding kernel (P04-T04), AC-01 issuance with exact journal lines (P04-T01), failed and concurrent numbering (P04-T02), the reporting-required block (P04-T05), partial credit and eligibility (P04-T03, AC-06), receipts with withholding, double allocation, allocation and receipt reversals with a balanced trial balance (AC-02, AC-05), credit limits, order conversion, delivery jobs and aging. `tests/domain.test.mjs` unit-tests the kernel.

## P04-03 API and jobs

The 34 P04 operations are served by `apps/api/src/workspace-api.mjs` through `@lara/contracts` with the shared conventions (X-Entity-Id, Idempotency-Key with request-hash receipts, If-Match on edits and actions, ETag on resources, typed errors): `/tax-rules` (create with the accounting-cases catalog as the golden-case registry, list, get, edit, approve, activate), `/invoices` (invoices and credit notes: create, list with `state`/`partyId` filters, get, edit, submit, approve, post, correct, deliver), `/sales-orders` (sales orders and quotations: create, list, get, edit, submit, approve, convert), `/collections` (create, list, get, edit, submit, approve, post, reverse, allocations), `POST /allocations/{id}/reverse` and `GET /open-items` (`partyId`, `side`, `open=true`). A document is addressable only through the family its kind belongs to (an invoice is 404 under `/sales-orders`). `POST /reports` accepts `reportType=aging`; `ledger.snapshotReport` gained pluggable builders so the aging report snapshots through the same immutable, checksummed path and renders to CSV. The P05 `/settlements` operations stay `FEATURE_NOT_ENABLED`.

Worker: `document.deliver` rechecks the requester's `invoice.deliver`, records the delivery as `sent` with a `<MAIL_ADAPTER>:<jobId>` provider reference (the mail adapter is local in this release; a qualified delivery adapter is an activation gate) and sets the document's `delivery_state` projection; the worker role can update only those columns. `report.generate` handles `aging`.

Verification: `scripts/test-p04-api.mjs` (six groups, API and worker as processes, also in CI for fresh and upgrade databases) covers the tax rule lifecycle over HTTP, invoice creation with server totals and contract rejection of client totals, idempotent replay, ETag/If-Match, forbidden and stale approvals, versioned issuance, posted immutability, filtered listing, correction eligibility and posting, collections with withholding and allocations, `ALLOCATION_EXCEEDS_BALANCE`, allocation and receipt reversals, delivery and aging jobs, and 404 isolation for unknown documents, foreign entities and mismatched kinds. `scripts/test-p02-api.mjs` now probes the later-phase gate with a P05 operation.

## P04-04 user journeys

`apps/web/src/app/_components/workspace-sales.tsx` adds the sales screens to the production composition (`/sales/invoices`, `/sales/invoices/{id}`, `/sales/orders`, `/sales/collections`, `/sales/collections/{id}`, `/sales/customers`, `/settings/tax-rules`), replacing the P04 roadmap placeholder in the navigation:

- Invoice list and editor: customer, branch, dates, lines with quantity, unit price, discount, price basis, revenue account (control accounts excluded) and tax rule; a client-side preview is labelled as such and the recorded totals come back from the server. Filters by state; the list shows document, delivery and settlement states side by side.
- Invoice detail: the four statuses (document, delivery, reporting, settlement) always shown separately, totals and outstanding, timeline, submit/approve/request changes/issue/deliver actions gated by permission and `If-Match`, immutable notice after issuance, draft editing, and the credit preview: remaining creditable net per revenue account after earlier credits, partial credit note or full reversal prepared as a linked draft.
- Orders and quotations: editor, submit, approve, convert once to an invoice draft.
- Receipts: editor with the allocation workbench (open items of the customer with outstanding amounts, "Full" shortcut, unapplied remainder shown as a customer advance), submit/approve/post/reverse, later application of the unapplied balance from the receipt page.
- Customers: receivables by customer, statement of open items, aging report as a job rendered from its snapshot.
- Tax rules: create draft versions from evidence and golden cases, approve and activate (separate principals), active versions immutable. The capabilities screen offers `sales` activation.

Read access to the chart and tax rules is extended to document preparers (`invoice.prepare`, `invoice.read`, `sales_order.create`, `collection.create`) because they are reference data for the editors; creation and editing keep their own permissions.

Verification: `tests/browser/workspace.spec.mjs` sales journey on the production composition — two-principal `sales` activation, control accounts through the chart screen, October period, tax rule approval and activation on screen, invoice with server totals through submit, approval and issuance to `INV-000001` with the four statuses, delivery through the worker, receipt with a full allocation through review and posting until the invoice shows `paid`, customer statement and aging job, WCAG checks on every sales route (also in CI on the production composition). The sales profile and numbering series are seeded through the runtime role because the contract has no operations for them yet.

## P04-05 acceptance and operations

Acceptance: P04-T01–T05 in `scripts/test-p04-domain.mjs` and `scripts/test-p04-api.mjs`; CORE regressions unchanged (P02/P03 suites pass with the P04 handlers registered); migration, restore and fresh/upgrade paths in `scripts/ci-database.mjs`. `scripts/test-p02-load.mjs` gained an issuance profile (prepare, submit, approve, issue with 10 concurrent workers) that asserts unique official numbers under concurrency and the p95 thresholds on the CI database. `docs/development/P04-RUNBOOK.md` covers activation gates, numbering incidents, issuance failures, corrections, receipts and allocations, delivery and reports. `docs/development/releases/0.4.0-draft.md` is the release draft for the owner; P04-06 stays blocked on the P03 release and owner sign-offs.

## Open items for the owner

- The P04 specification lists `payment_terms`, `credit_limits`, `deliveries` and `party_snapshot` but the reviewed OpenAPI has no operations for payment terms, numbering series, credit limits or delivery listing; the tests seed series and limits directly and the P04-04 screens will need read/list and versioned-mutation operations added to the contract for them (series and the `sales_profile` settings at minimum), following the phase rule.
- `DocumentResource.lines` has no room for the computed per-line tax (`additionalProperties: false`); the screens show header totals only until the contract adds line results.
- `POST /invoices/{id}/deliver` carries no recipient; delivery uses the party's `address_json.email` when present and otherwise records a copy for manual handover.
- No seeded role template holds `sales_order.approve` or `sales_order.convert`; tenants must create a role for order approval (the domain test does). Consider adding them to `controller` or `billing` in a later seed migration.
- Tax rules and the kernel treat `applicabilityProfileId` as an opaque approved-profile reference; the P07 profile registry will bind it.
- `ADR 001` still names NestJS/Vitest; the codebase remains plain Node + `node:test` (see `P02-REVIEW.md`).
